## Starting point

Phase 5 left tombstones permanent by design: a delete sets `deleted_at` and the
row's file stays in the sync folder announcing the delete to every machine that
reads it. The carried-forward note said it plainly — "a note deleted years ago
keeps its file forever ... a 'compact the sync folder' command would be the
answer."

Nothing in the repo touched the problem: no `compact`, `prune`, `purge` or
`vacuum` anywhere. This was greenfield on top of a settled Phase 5.

## What was built

### `study/compact.go` — the only place a row is physically removed

Eight small functions in two halves: `ExpiredNotes`/`ExpiredTags`/
`ExpiredXrefs`/`ExpiredSermons` list ids tombstoned before a cutoff, and
`PurgeNotes`/`PurgeTags`/`PurgeXrefs`/`PurgeSermons` remove them with their
children. Both halves sit on `expiredIn` and `purgeRows`.

Finding and removing are separate calls on purpose: the syncer has to delete a
row's *file* as well as the row, so it needs the id list in hand — and a dry run
is then simply the find without the purge.

### `syncer/compact.go` — the pass

`Compact(retention, dryRun)` plus `CompactReport`/`EntityCompaction` and a
generic `compactEntity`, mirroring the shape of `syncEntity`: the four passes
differ only in which table is read and which purge is called.

### Supporting changes

- `study/sync.go` — `Syncable` gained `SyncDeleted() time.Time`, so compaction
  can ask a record whether it is dead without knowing which kind it is.
- `syncer/syncer.go` — `run` split into `run` / `runLocked`.
- `syncer/files.go` — `removeRecord`; `readRecords` now takes a `problemSink`.
- `syncer/report.go` — `problemSink`, and `kindLabel` shared by both reports.
- `main.go` — the `compact` subcommand, hand-parsed args, the printed report.
- `web/ui/pages.go` — one sentence on the sync card. Not a button.

## Design decisions worth keeping

### Import first, under one hold of `runMu`

Compaction deletes a file, which is the only record of an event. Anything the
folder is still holding therefore has to be applied before that happens — an
undelete written on the other machine, or a delete this machine has not seen.
An import pass makes the database the complete picture, so every question
compaction then asks can be answered from it. Importing is not destructive; it
is what `serve` already does at startup.

Both halves run under one hold of `runMu`, which is why `run` was split into
`run` (takes the lock) and `runLocked` (the body). A debounced export slipping
in between them would rewrite files the pass had already decided to delete.

### The retention window is the whole safety

Nothing in this process can see how long a second machine has been away. The
window is the only thing standing between compaction and a laptop that was in a
drawer all season, still holding the row alive and ready to export it back.
Ninety days, and the cost of waiting is a few hundred bytes per dead row — there
is nothing to buy by being aggressive.

### `purgeRows` narrows the id list before deleting anything

The id list is assembled from a sync folder as well as from the local database,
and a file claiming a row is dead is not the same thing as the row being dead
here. `tombstonedIDs` narrows against `deleted_at IS NOT NULL` inside the
transaction, and the child deletes run on the *narrowed* list — narrowing after
would take a live note's anchors with it. That ordering is the whole safety of
the file, and it has its own test.

### The row goes before its file

A crash between the two leaves a file with no row, which the next reconciliation
re-imports as a tombstone and the next compaction removes again. The other order
leaves a row with no file, which exports itself straight back and looks like the
compaction never happened.

### Expiry is strictly before the cutoff

An equal clock is the same tie `syncer.newer` refuses to break, and compaction
is not the place to start breaking it. The cutoff is truncated to microseconds
for the reason everything else in this engine is: that is the precision bytdb
keeps.

### The orphan branch is what finally clears merged-tag files

This one was discovered by the test, not designed up front. `ApplyNote` creates
tags **by name** (via `writeTagLinks` → `ensureTag`) before the tag's own file is
ever read, so every machine mints its own id for a shared tag and the folder ends
up holding one redundant file per machine per name. Those ids have no local row
and never will, so the row-driven path cannot reach them — only compaction can,
and it does once the record they carry is an expired tombstone.

The two-host test caught this as a "5 files removed, 4 rows removed" mismatch.
The code was right; the expectation was not. It is now an assertion with the
reason written next to it.

### A command, not a button

Every other maintenance action in this app is additive or reversible. This one
is neither, and the number that makes it safe is one only the user can choose.
The settings card gained a sentence pointing at the command instead of a third
button.

### No database-only mode

`compact` requires a sync directory. bytdb's file is append-only, so `DELETE`
reclaims nothing on disk; compacting a database with no sync folder would spend
a destructive pass to save nothing. The saving is in the folder — one JSON file
per dead row, kept forever, in a directory a daemon re-uploads. Somebody wanting
the database itself smaller wants `pbstudy backup`, which writes a fresh file.

### Dry run reports a forecast, not a receipt

`EntityCompaction` carries `DryRun` so the per-entity line reads "1 row to
remove" rather than "1 row removed". Caught on the first live run, when the
headline said "Would remove" over lines that claimed the work was done.

## End-to-end verification (real binary, real server, scratch sandbox)

| Check | Result |
| --- | --- |
| Two notes + two tags + a sermon created over HTTP | 5 files exported ~2 s later |
| Note, tag and sermon deleted | all three files carry `deletedAt` |
| `compact` (default 90 days) | "Nothing was old enough to remove (3 tombstones still inside the window)" |
| `compact 0 --dry-run` | "Would remove 3 tombstones and 3 files"; lines read "to remove"; nothing changed on disk |
| `compact 0` | removed exactly what the dry run predicted |
| Second `compact 0` | "Nothing was old enough to remove" |
| `sync` afterwards | "Everything was already in step" — no resurrection |
| Live note after compaction | notes list, permalink, tag and anchor all intact |
| Purged note permalink | 404 |
| Tags page / sermons page | only the kept tag; the deleted sermon gone |
| `compact` while `serve` holds the lock | refused, names the PID |
| `compact seven` | refused, with the usage line |
| `compact` with no `PBSTUDY_SYNC_DIR` | refused, explains why a DB-only pass would save nothing |
| `/settings` | renders the new sentence, `<code>` intact, 200 |

## Tests added

| File | Covers |
| --- | --- |
| `study/compact_test.go` | children removed with the row; a live row refused even when handed in with a tombstone (and keeping its children); strictly-before-the-cutoff tie rule; tag links cleared; purged rows no longer export; the empty-list `IN ()` boundary |
| `syncer/compact_test.go` | expired tombstones removed row-and-file; recent ones kept and counted; dry run matches the real pass and changes nothing; orphaned tombstone files removed while the tag they merged into survives; a folder with no deletes untouched; two-host convergence with no resurrection; no `.bytdb` or `.tmp` left behind |

The time dimension is handled without sleeping or writing timestamps behind the
API's back: a negative retention puts the cutoff in the future so every tombstone
is expired, a positive one puts it in the past so none is. The rows under test
are then the ones the real code paths made.

### Carried forward

- **Live-tag duplicate files still accumulate** — one per machine per name.
  Compaction clears them once they are *tombstoned*, but a shared live tag keeps
  its redundant file on every machine. A different cleanup than this one.
- **A successful live AI draft has still never been observed** (no
  `ANTHROPIC_API_KEY` in these sessions).
- **ScriptTagger hover popups in a real browser**, unverified since Phase 2 —
  the Chrome instance here cannot reach this machine's localhost.
- **Two machines editing the same note while both are offline still loses one
  side.** Accepted for a single user; the snapshots are the net.
- **Only the syncer path installs a signal handler.** With no sync directory
  configured, `SIGTERM` still kills the process without closing the databases.
- **Compaction is per machine and has to be run on each.** A machine that has
  not compacted re-exports its tombstone files; the others import and remove them
  again next pass. Bounded churn, converges once both compact, and what comes
  back is a tombstone — invisible to every read in `study/`.
- The dev sandbox is still `PBSTUDY_DATA_DIR=/tmp/pbstudy-dev go run . serve`.
  This session used a throwaway sandbox under the scratchpad instead, so the dev
  data was never touched.
