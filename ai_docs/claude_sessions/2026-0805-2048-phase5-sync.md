## Starting point

Phases 1–4 had already put the shape of this in place: every syncable row
carries a UUID id, a UTC `updated_at` and a `deleted_at` tombstone, deletes
never remove rows, and `bible.Ref` gained lower-camel JSON tags in Phase 4
specifically so it could travel in these files. Nothing had ever read or
written the sync directory.

The first thing measured was what the clock is actually worth. **bytdb stores
`TIMESTAMP` at microsecond precision** — a value written with nanoseconds reads
back truncated. That single fact shaped two decisions below.

## What was built

### `study/sync.go` — the record layer

Four record types (`NoteRecord`, `TagRecord`, `XrefRecord`, `SermonRecord`), a
whole-table export per entity, and an idempotent apply per entity. The records
are deliberately **not** the domain types: `Note`/`Tag`/`CrossRef`/`Sermon` are
shaped for the pages that show them — tombstones filtered out, tag links
resolved, an unexported field recording which end an xref was loaded from — and
a record has the opposite job. It must carry tombstones, stay stable across
versions of this program, and be readable in a text editor by someone who is
worried. One type serving both would make every display change a change to the
format of files already sitting in someone's iCloud folder.

### `syncer/` — the reconciliation

`syncer.go` (the merge and the debounce), `files.go` (atomic writes, folder
scanning, the id-as-filename guard), `report.go` (what a pass did).

`syncEntity` is generic over the record type: the four passes differ only in
which table is read and which apply is called, and everything else — the
decode, the version check, the clock comparison, the atomic write, the counting
— is identical.

### `web/handlers_sync.go`, `ui/pages.go` — the settings page

`POST /sync/run` and `POST /backup`, both POST-then-redirect with the outcome
held on the server, so a refresh re-reads the report rather than running a
second sync. The sync card shows the folder, the two buttons, the last report
and the recent snapshots.

### `main.go` — the lifecycle

Startup import, a `sync` subcommand, and a SIGINT/SIGTERM handler that flushes
before exit.

## Design decisions worth keeping

### Import is one pass, export is another

A single interleaved pass would decide a row's fate against a snapshot taken
before its own import changed it — and then immediately write back what it had
just taken in. Import runs over the whole folder first; export re-reads the
database.

### Tag identity forced a second clock comparison

The syncer decides what to import by comparing a file against the local row
**with the same id**. Two machines that both created "Grace" offline have two
ids for it, and the unique index on `tags.name` makes inserting the second one
impossible — so id-matching cannot even represent the case.

`ApplyTag` therefore matches on the folded name and makes its own clock
comparison, reporting one of three outcomes (`TagWritten`, `TagMerged`,
`TagUnchanged`). Without that second comparison the merge rewrites a timestamp
on every run, the next run exports it, and the two machines trade the same tag
forever — a sync that never converges and keeps waking the daemon up.

The local id survives the merge, so the cost is one redundant file per machine
in `tags/`. The live check showed exactly the intended end state: 2 tags, 4
files, "nothing to do".

### The clock is compared at the precision the storage keeps

`syncer.newer` truncates both sides to microseconds. Raw comparison would make
a freshly imported row look permanently older than the file it came from, and
every run would re-import it. Ties lose — an equal clock is not evidence of a
change. Every record is built from a database read rather than an in-memory
value, so `RFC3339Nano` round-trips exactly.

### One middleware, not a call in twelve handlers

Every mutation in this app is a POST that ends in a redirect or a re-render, so
the auto-export hook lives where that rule lives: `Server.syncOnWrite` calls
`Touch` after any POST that did not fail. Failed requests are excluded, `Touch`
never blocks, and the 2-second debounce collapses a burst of outline edits into
one export.

### The report is the feature

Sync is the one thing in this app whose success is invisible — nothing on
screen changes when it works, so a silent pass that failed to import the note
written on the other machine is indistinguishable from one that had nothing to
do. Every pass counts both directions, names every file it could not use, and
says out loud when a tag was merged by name. Problems are collected rather than
returned, so one broken file never stops the pass and never vanishes either.

### Three kinds of file are refused, not guessed at

Unreadable JSON, a record whose `kind` does not match its folder, and a record
whose format version is **newer than this binary**. The last one matters most:
importing what we can parse would drop what we cannot, and the export half of
the same run would then write that loss back over the file. All three are left
on disk untouched.

### `cfg.Load` refuses overlapping directories

The plan warned never to let a sync daemon touch the live database. A warning
is not a mechanism. Startup now fails if the sync dir is the data dir, or if
either contains the other — compared segment-wise, so `pbstudy-sync` is not
read as living inside `pbstudy`.

### An id from a file must never become a path

`recordFileName` accepts only `[A-Za-z0-9_-]`, up to 128 characters. Ids are
UUIDs this app minted — until one arrives from a machine, or a hand edit, that
this app did not write. Rejecting outright beats sanitizing: a record whose id
is not an id is not a record.

## Deviations from the plan

- **No download buttons on the settings page.** The route sketch listed them;
  downloading 66 books from a web handler needs its own progress stream and
  concurrency guard, and `pbstudy download` already does the job. Settings
  gained the sync and backup buttons instead.
- **A `pbstudy sync` subcommand was added** — the same engine without the
  server, so a cron job or a git hook can run it. It cannot run while `serve`
  holds the data-directory lock, which is the correct answer.
- **Sermon `status` is normalized on import**, closing the Phase 4
  carried-forward item: an incoming `drafting` becomes `drafted` if there is
  draft text and `outline` if there is not. "drafting" describes a generator
  running in a process, possibly one that crashed on the other machine.
- **The syncer package is three files, not the plan's `export.go`/`import.go`
  split.** The two directions share the decode, the clock rule and the report;
  splitting by direction would have put half of each in both files.
